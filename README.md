# Репозиторий сельскохозяйственных данных MVP

MVP-прототип выпускной квалификационной работы на тему: «Разработка репозитория данных для сельского хозяйства».

Проект реализует локальный прототип репозитория агроданных: набор данных хранится отдельно от его версий, к версии привязаны метаданные, файлы, результаты проверки, импортированные наблюдения и факты экспорта. Это не production-система, а демонстрационный MVP для проверки основной логики загрузки, валидации, хранения и выгрузки сельскохозяйственных наблюдений.

## Текущий статус

- Приложение запускается локально через Docker Compose.
- Backend: FastAPI, SQLAlchemy, PostgreSQL.
- Frontend: Streamlit.
- Хранилище исходных файлов: локальная папка `storage/`.
- База данных: PostgreSQL в Docker volume `postgres_data`.
- Тесты backend на текущей версии проходят: `10 passed`.

## Быстрый запуск

Из корня проекта:

```bash
docker compose up -d --build
```

После запуска:

- Streamlit UI: http://localhost:8502
- FastAPI Swagger UI: http://localhost:8000/docs
- PostgreSQL: `localhost:5432`

Важно: внутри контейнера Streamlit может писать в логах `http://0.0.0.0:8501`, но с компьютера приложение открывается по адресу http://localhost:8502, потому что в `docker-compose.yml` настроен проброс порта `8502:8501`.

Проверить состояние контейнеров:

```bash
docker compose ps
```

Остановить приложение без удаления базы данных:

```bash
docker compose stop
```

Полностью убрать контейнеры, но сохранить volume базы:

```bash
docker compose down
```

Не используйте `docker compose down -v`, если нужно сохранить данные: эта команда удалит volume PostgreSQL.

## Первичная инициализация

После первого запуска нужно заполнить справочники и demo-пользователей:

```bash
curl -X POST http://localhost:8000/seed
```

То же действие доступно в Streamlit на экране входа кнопкой «Заполнить справочники и demo-пользователей».

Seed создает справочники и demo-пользователей, но не создает готовые наборы данных. В чистой базе после seed наборы нужно создать через интерфейс и загрузить CSV-файлы из `sample_data/`.

## Demo-пользователи

- `admin@example.com` / `admin123` — администратор.
- `moderator@example.com` / `moderator123` — модератор.
- `user@example.com` / `user123` — обычный пользователь.

Авторизация в MVP демонстрационная. На текущем этапе нет JWT, OAuth, полноценной серверной сессии и промышленной RBAC-модели.

## Demo-наборы данных

В репозитории есть три sample CSV-файла:

- `sample_data/sample_observations.csv` — пример агрономических наблюдений.
- `sample_data/sample_weather_observations.csv` — пример погодных наблюдений.
- `sample_data/sample_livestock_observations.csv` — пример наблюдений по животноводству.

Ожидаемая структура CSV:

```csv
region,agro_object,indicator,unit,period_year,value
```

## Основной пользовательский сценарий

1. Открыть http://localhost:8502.
2. Войти под demo-пользователем.
3. При необходимости нажать «Заполнить справочники и demo-пользователей».
4. Открыть раздел «Создание набора данных».
5. Пройти мастер создания:
   - набор данных;
   - версия;
   - метаданные;
   - файл;
   - импорт наблюдений;
   - проверка результата.
6. Открыть карточку набора данных.
7. Проверить версию, метаданные, файлы, наблюдения.
8. При необходимости скачать исходный файл или экспортировать наблюдения в CSV.

Отдельные страницы старого сценария тоже сохранены: можно вручную перейти к созданию версии, метаданным, загрузке файла, карточке набора, наблюдениям и журналу экспортов.

## Страницы Streamlit-интерфейса

- «Обзор» — сводные счетчики по наборам, версиям, файлам, наблюдениям и экспортам.
- «Аналитика» — агрегированные показатели по регионам, показателям и агрообъектам.
- «Каталог данных» — поиск и фильтрация наборов данных.
- «Создание набора данных» — пошаговый мастер создания полного набора.
- «Создание версии» — ручное создание версии для существующего набора.
- «Метаданные версии» — заполнение и обновление описательных метаданных версии.
- «Загрузка файла» — загрузка CSV/XLSX, проверка и импорт наблюдений.
- «Карточка набора данных» — просмотр общей информации, версий, файлов, экспорта и наблюдений.
- «Наблюдения» — просмотр импортированного аналитического слоя с фильтрами.
- «Журнал экспортов» — список фактов скачивания и экспорта.

## Реализованные таблицы базы данных

- `users`, `roles`, `user_roles` — demo-пользователи и роли.
- `access_levels`, `categories`, `formats`, `licenses`, `dataset_statuses`, `data_sources` — справочники репозитория.
- `regions`, `agro_objects`, `indicators`, `measurement_units` — справочники аналитических наблюдений.
- `datasets` — постоянная карточка набора данных.
- `dataset_versions` — версии набора данных, текущая версия и статус.
- `dataset_metadata` — описательные метаданные версии.
- `dataset_files` — загруженные исходные файлы, размер, формат, checksum, флаг основного файла.
- `keywords`, `version_keywords` — ключевые слова версии.
- `observations` — структурированные импортированные наблюдения.
- `validation_results`, `validation_errors` — результаты проверки файлов и ошибки валидации.
- `data_exports` — журнал скачиваний исходных файлов и экспортов наблюдений.

## Реализованные API endpoints

- `GET /health` — проверка работоспособности API.
- `POST /seed` — заполнение справочников и demo-пользователей.
- `POST /auth/login` — demo-вход пользователя.
- `GET /references` — получение справочников для интерфейса.
- `GET /dashboard` — данные для обзорной страницы.
- `GET /analytics` — агрегированные данные для аналитики.
- `GET /catalog/datasets` — каталог наборов с фильтрами.
- `POST /datasets` — создание набора данных.
- `POST /datasets/{dataset_id}/versions` — создание версии набора.
- `POST /versions/{version_id}/make-current` — назначение текущей версии.
- `POST /versions/{version_id}/metadata` — создание или обновление метаданных версии.
- `POST /versions/{version_id}/files` — загрузка и проверка CSV/XLSX-файла.
- `POST /files/{file_id}/import-observations` — импорт наблюдений из проверенного файла.
- `GET /datasets/{dataset_id}` — карточка набора данных.
- `DELETE /datasets/{dataset_id}` — удаление набора данных администратором.
- `DELETE /versions/{version_id}` — удаление версии администратором.
- `DELETE /files/{file_id}` — удаление файла администратором.
- `GET /versions/{version_id}/observations` — просмотр наблюдений версии.
- `GET /files/{file_id}/download` — скачивание исходного файла с записью в `data_exports`.
- `GET /versions/{version_id}/export-observations` — экспорт наблюдений в CSV с записью в `data_exports`.
- `GET /exports` — журнал экспортов.
- `GET /exports/detailed` — расширенный журнал экспортов для интерфейса.

## Что реализовано в загрузке и импорте

- Загрузка CSV/XLSX-файлов в локальную папку `storage/`.
- Расчет размера файла и SHA-256 checksum.
- Базовая проверка структуры файла.
- Запись результатов проверки в `validation_results` и `validation_errors`.
- Проверка обязательных колонок.
- Импорт строк в таблицу `observations`.
- Проверка ссылок на справочники при импорте: регион, агрообъект, показатель, единица измерения.
- Предупреждение о повторной загрузке файла с тем же checksum в пределах версии.
- Отображение повторно загруженных файлов с различимыми именами: например, `file.csv`, `file (2).csv`.
- При повторном импорте дубля наблюдения от предыдущих дублей того же файла заменяются, чтобы не плодить одинаковые строки.

## Скачивание и экспорт

- Исходный файл можно скачать из карточки набора данных.
- Наблюдения текущей версии можно экспортировать в CSV.
- Оба действия фиксируются в таблице `data_exports`.
- В журнале экспортов отображаются факты скачивания и выгрузки.

## Административные действия

Для пользователя с ролью `admin` в интерфейсе доступны:

- удаление набора данных;
- удаление версии;
- удаление файла.

Удаление в текущем MVP является физическим. Полноценный soft delete, восстановление, расширенный аудит и журнал административных действий не реализованы.

## Тесты

Запуск тестов в контейнере backend:

```bash
docker compose exec -T backend pytest
```

Локальный запуск из папки `backend`:

```bash
cd backend
pytest
```

Сейчас тесты покрывают:

- `GET /health`;
- создание набора, версии и метаданных;
- переключение текущей версии;
- загрузку валидного CSV;
- ошибку при отсутствии обязательной колонки;
- обработку повторной загрузки файла;
- импорт наблюдений без дублирования;
- экспорт наблюдений и запись в `data_exports`;
- удаление файла, версии и набора администратором;
- запрет удаления набора обычным пользователем.

Frontend-тестов и end-to-end тестов браузерного сценария пока нет.

## Чем MVP отличается от полной модели v4.1

В полной проектной модели v4.1 предполагаются более развитые механизмы происхождения данных, аудита, правил качества, интеграций и геообработки. В MVP эти части намеренно упрощены.

| Направление | В MVP | В полной модели v4.1 / развитии |
| --- | --- | --- |
| Источники версии | `source_id` хранится прямо в `dataset_versions` | отдельная история источников версии |
| Статусы | текущий статус хранится на версии | история изменения статусов |
| Авторизация | demo-вход и простые роли | JWT/OAuth, полноценная RBAC-модель |
| Валидация | базовые проверки CSV/XLSX и справочников | настраиваемые правила качества, диапазоны, аномалии |
| Аудит | фиксируются экспорты | полный audit log действий пользователей |
| Удаление | физическое удаление админом | soft delete, восстановление, журнал причин |
| Геоданные | справочник регионов | PostGIS, геометрии, пространственные запросы |
| Интеграции | не реализованы | внешние API/ФГИС/официальные источники |
| Демо-данные | sample CSV загружаются вручную | воспроизводимый seed demo-наборов |
| Миграции БД | `Base.metadata.create_all` | Alembic-миграции |

## Не реализовано в MVP

- Полноценная промышленная авторизация.
- Alembic-миграции.
- Soft delete и восстановление удаленных данных.
- Расширенный audit log всех действий.
- Настраиваемые правила валидации.
- Проверки диапазонов, выбросов и совместимости единиц измерения.
- PostGIS и пространственная аналитика.
- Интеграции с внешними государственными API/ФГИС.
- Автоматический seed готовых demo-наборов данных.
- Frontend/e2e-тесты.
- Production-деплой.

## Если Docker не скачивает образы

Если при сборке появляется ошибка вида `failed to connect to the docker API`, сначала проверьте, что Docker Desktop запущен.

Если появляется ошибка вида `lookup docker-images-prod...cloudflarestorage.com` или `failed to fetch anonymous token`, проблема обычно находится не в коде проекта, а в доступе Docker Desktop к Docker Hub/CDN. Возможные решения:

1. Включить VPN/прокси именно для Docker Desktop, а не только для браузера.
2. В Docker Desktop открыть `Settings -> Resources -> Proxies` и указать HTTPS proxy, если он используется в сети.
3. В Docker Desktop открыть `Settings -> Docker Engine` и добавить DNS:

```json
{
  "dns": ["8.8.8.8", "1.1.1.1"]
}
```

После изменения настроек перезапустите Docker Desktop и выполните:

```bash
docker compose pull
docker compose up -d --build
```

Отдельно проверить скачивание базовых образов:

```bash
docker pull python:3.11-slim
docker pull postgres:16-alpine
```
