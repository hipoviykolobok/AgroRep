# Описание MVP-прототипа для главы 3

Данный файл описывает фактически реализованное состояние проекта `repository_mvp`. Описание составлено по текущим файлам backend, frontend, Docker Compose и pytest-тестам. Новые функции в рамках подготовки документации не добавлялись.

## 3.1 Реализация базы данных MVP-прототипа

MVP-прототип реализует репозиторий сельскохозяйственных данных, в котором постоянная карточка набора данных отделена от изменяемого состояния версии. Таблица `datasets` хранит только устойчивые сведения о наборе, а статус, доступ, источник, метаданные, файлы, наблюдения, результаты проверки и экспорт относятся к версии или связанным с ней объектам.

База данных описана SQLAlchemy-моделями в файле `backend/app/models.py`. Таблицы создаются при старте backend через `Base.metadata.create_all(...)`, вызванный из `backend/app/database.py`. В промышленной версии вместо такого подхода предполагается использовать миграции, однако для MVP этого достаточно для демонстрационного запуска.

## 3.2 Разработка backend и frontend

Backend реализован на FastAPI. Он предоставляет API для авторизации, заполнения справочников, управления наборами и версиями, загрузки файлов, проверки, импорта наблюдений, экспорта данных, просмотра журнала экспортов и получения агрегированных данных для обзорных экранов.

Frontend реализован на Streamlit. Пользовательский интерфейс работает на русском языке, а backend и база данных сохраняют англоязычные технические имена полей и таблиц. Такой подход разделяет внутренний API-контракт и пользовательское отображение.

### Docker Compose

В `docker-compose.yml` реализованы три сервиса:

| Сервис | Назначение | Порт |
|---|---|---|
| `db` | PostgreSQL 16 Alpine | `5432` |
| `backend` | FastAPI-приложение | `8000` |
| `frontend` | Streamlit UI | `8501` |

Для PostgreSQL используется volume `postgres_data`. Для файлового хранилища используется bind mount `./storage:/app/storage`.

### API endpoints

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/health` | Проверка работоспособности backend |
| `POST` | `/seed` | Заполнение справочников и demo-пользователей |
| `POST` | `/auth/login` | Простая авторизация по email/password |
| `GET` | `/references` | Получение справочников для frontend |
| `GET` | `/dashboard` | Сводные показатели для страницы обзора |
| `GET` | `/analytics` | Агрегированные данные для диаграмм |
| `GET` | `/catalog/datasets` | Получение каталога наборов с фильтрами |
| `POST` | `/datasets` | Создание карточки набора данных |
| `POST` | `/datasets/{dataset_id}/versions` | Создание версии набора |
| `POST` | `/versions/{version_id}/metadata` | Создание или обновление метаданных версии |
| `POST` | `/versions/{version_id}/files` | Загрузка файла, сохранение в storage и базовая проверка |

| `GET` | `/exports/detailed` | Получение детального журнала экспортов для UI |

### Валидация файлов

Валидация реализована в `backend/app/validators.py`. Поддерживаются файлы `.csv` и `.xlsx`. Проверяются:

- формат файла;
- возможность чтения файла;
- непустой файл;
- наличие обязательных колонок `region`, `agro_object`, `indicator`, `unit`, `period_year`, `value`;
- числовой формат `period_year`;
- числовой формат `value`.

При импорте дополнительно проверяется наличие `region`, `agro_object`, `indicator` и `unit` в справочниках. Результаты записываются в `validation_results`, а ошибки - в `validation_errors`.

## 3.3 Реализованные пользовательские сценарии

### Страницы Streamlit UI

| Страница | Назначение и сценарии |
|---|---|
| `Вход` | Авторизация demo-пользователя, запуск seed |
| `Обзор` | Просмотр количества наборов, версий, файлов, наблюдений и экспортов |
| `Аналитика` | Диаграммы по категориям, регионам, показателям и агрообъектам |
| `Каталог данных` | Поиск и фильтрация наборов данных |
| `Создание набора данных` | Создание постоянной карточки `datasets` |
| `Создание версии` | Создание `dataset_versions` |
| `Метаданные версии` | Заполнение описания, методики, охвата, лицензии и качества |
| `Загрузка файла` | Загрузка CSV/XLSX, проверка, просмотр ошибок, импорт observations |
| `Карточка набора данных` | Просмотр карточки, версии, метаданных, файлов, наблюдений, скачивание и экспорт |
| `Наблюдения` | Просмотр аналитического слоя с фильтрами |
| `Журнал экспортов` | Просмотр зафиксированных экспортов и скачиваний |

### Основной демонстрационный сценарий

1. Пользователь входит под demo-учетной записью.
2. При необходимости запускает заполнение справочников.
3. Создает карточку набора данных.
4. Создает версию набора.
5. Заполняет метаданные версии.
6. Загружает CSV/XLSX-файл.
7. Система сохраняет файл в `storage/`, считает checksum и выполняет проверку.
8. Пользователь импортирует корректные строки в `observations`.
9. Пользователь находит набор в каталоге и открывает карточку.
10. Пользователь скачивает исходный файл или экспортирует observations.
11. Система фиксирует факт экспорта в `data_exports`.
12. Пользователь просматривает журнал экспортов и аналитические диаграммы.

## 3.4 Тестирование и ограничения MVP

### Pytest-тесты

| Файл теста | Проверяемый сценарий | Ожидаемый результат |
|---|---|---|
| `test_health.py` | `GET /health` | Возвращается `{"status": "ok"}` |
| `test_datasets.py` | Создание dataset, версии и метаданных | Все сущности создаются и связываются по `version_id` |
| `test_validation.py` | Корректный CSV | Проверка завершается со статусом `success` |
| `test_validation.py` | CSV без обязательной колонки | Проверка завершается со статусом `failed`, создается ошибка |
| `test_exports.py` | Импорт observations и экспорт CSV | Экспорт выполняется, запись появляется в `data_exports` |

Фактический вывод тестов сохранен в файле `docs/diploma/test_results.txt`.

### Уточнения по результатам сверки

В предыдущем кратком техническом описании в целом корректно отражены реализованные компоненты. По фактической сверке стоит отдельно уточнить:

- в рабочей папке присутствуют локальные runtime-артефакты: `backend/.venv`, `backend/.pytest_cache`, загруженные файлы в `storage/`; они не являются обязательной частью исходной структуры MVP;
- таблицы `keywords` и `version_keywords` реализованы в SQLAlchemy-моделях, но отдельные endpoints и страницы UI для управления ключевыми словами не реализованы;
- endpoint `GET /exports` реализован и используется тестом, а frontend использует более подробный endpoint `GET /exports/detailed`;
- `GET /analytics` и `GET /dashboard` являются вспомогательными read-only endpoints для Streamlit-страниц, их не было в исходном минимальном перечне, но они уже реализованы в текущем состоянии проекта;
- миграции Alembic отсутствуют, таблицы создаются через `create_all`.

### Ограничения MVP

- отсутствуют Alembic-миграции;
- отсутствует JWT/OAuth;
- роли реализованы упрощенно, без промышленной RBAC-модели;
- отсутствует история изменения статусов версии;
- отсутствует отдельная таблица `version_sources`, источник хранится в `dataset_versions.source_id`;
- отсутствует `audit_log`;
- отсутствует таблица и UI для редактирования правил проверки `validation_rules`;
- отсутствует PostGIS и расширенная геообработка;
- отсутствуют интеграции с внешними ФГИС/API;
- отсутствуют нейросетевые подсказки метаданных;
- Streamlit UI является демонстрационным интерфейсом, а не промышленным frontend.

### Направления дальнейшего развития

- внедрить Alembic для миграций БД;
- добавить историю статусов `version_status_history`;
- вынести источники версий в `version_sources`;
- реализовать `validation_rules` для настраиваемых правил проверки;
- добавить `audit_log`;
- расширить работу с ключевыми словами на уровне API и UI;
- добавить PostGIS для геопространственных данных;
- реализовать полноценную модель ролей и прав;
- подключить внешние источники и государственные информационные системы;
- расширить аналитические панели и экспортные форматы;
- заменить Streamlit на отдельный frontend при переходе к промышленной реализации.
