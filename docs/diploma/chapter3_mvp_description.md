# Описание MVP-прототипа для главы 3

Данный файл фиксирует фактическое состояние проекта `repository_mvp` на текущей версии. Описание составлено по реализованным файлам backend, frontend, Docker Compose, sample-данным и результатам pytest. Новые функции в рамках подготовки документации не добавлялись.

MVP-прототип реализует базовый жизненный цикл репозитория сельскохозяйственных данных: создание карточки набора, создание версии, заполнение метаданных версии, загрузку файла, базовую проверку структуры, импорт наблюдений, просмотр карточки, скачивание исходного файла, экспорт структурированных наблюдений и фиксацию операций экспорта.

Проект является локальным MVP, а не production-системой. Полноценная промышленная авторизация, OAuth/JWT, Alembic-миграции, soft delete, общий audit log, PostGIS, внешние ФГИС/API-интеграции и production-деплой не реализованы.

## 3.1 Реализация базы данных MVP-прототипа

База данных MVP-прототипа предназначена для демонстрации основного жизненного цикла сельскохозяйственных данных. В ней реализованы сущности для хранения пользователей, ролей, справочников, карточек наборов данных, версий, метаданных, загруженных файлов, результатов проверки, структурированных наблюдений и операций экспорта.

Ключевая архитектурная идея полной модели сохранена: постоянная карточка набора данных отделена от его версий. Таблица `datasets` хранит устойчивые сведения о наборе данных, а таблица `dataset_versions` хранит конкретные версии. К версии привязываются метаданные, файлы, результаты проверки, наблюдения и операции предоставления данных пользователю.

Таблицы создаются при старте backend через `Base.metadata.create_all`. Это допустимо для MVP, но не является промышленным механизмом управления схемой. Для дальнейшего развития требуется внедрение Alembic-миграций.

### Демонстрационные данные и справочники

Заполнение справочников выполняется через `POST /seed` или кнопку seed на экране входа. Seed создает справочники и demo-пользователей, но не создает готовые записи `datasets`, `dataset_versions` и `observations`. Наборы данных и версии создаются пользователем через интерфейс или API.

В проекте есть три демонстрационных CSV-файла:

| Файл | Назначение |
|---|---|
| `sample_data/sample_observations.csv` | Пример агрономических наблюдений |
| `sample_data/sample_weather_observations.csv` | Пример погодных наблюдений |
| `sample_data/sample_livestock_observations.csv` | Пример наблюдений по животноводству |

Ожидаемая структура файлов:

```csv
region,agro_object,indicator,unit,period_year,value
```

## 3.2 Разработка серверной и клиентской частей MVP-прототипа

Архитектура MVP построена по трехуровневому принципу: PostgreSQL и локальное файловое хранилище отвечают за хранение данных, FastAPI выполняет серверную логику, Streamlit предоставляет пользовательский интерфейс.

### Компоненты проекта

| Компонент | Технология | Назначение |
|---|---|---|
| База данных | PostgreSQL | Хранение карточек наборов, версий, метаданных, справочников, наблюдений и экспортов |
| Файловое хранилище | Локальная папка `storage/` | Хранение исходных загруженных файлов и экспортированных CSV |
| Backend | FastAPI | API, бизнес-логика, работа с БД и файлами |
| ORM | SQLAlchemy | Описание моделей и операции с таблицами |
| Frontend | Streamlit | Пользовательский интерфейс MVP |
| Обработка файлов | pandas, openpyxl | Чтение CSV/XLSX |
| Тестирование | pytest | Проверка backend-сценариев |
| Запуск | Docker Compose | Совместный запуск `db`, `backend`, `frontend` |

### Docker Compose

В `docker-compose.yml` реализованы три сервиса:

| Сервис | Назначение | Порт |
|---|---|---|
| `db` | PostgreSQL 16 Alpine | `5432` |
| `backend` | FastAPI-приложение | `8000` |
| `frontend` | Streamlit UI | `8502` на хосте, `8501` внутри контейнера |

Локальные адреса:

- Streamlit UI: `http://localhost:8502`;
- FastAPI Swagger UI: `http://localhost:8000/docs`.

Основные команды:

```bash
docker compose up -d --build
docker compose ps
docker compose exec -T backend pytest
docker compose stop
docker compose down
```

Команда `docker compose down -v` удаляет volume PostgreSQL и не должна использоваться, если необходимо сохранить данные.

## 3.3 Реализованные пользовательские сценарии

### Пошаговый мастер создания набора

На странице `Создание набора данных` реализован мастер, объединяющий основной пользовательский сценарий в одной последовательности. Пользователь не должен вручную работать с `dataset_id`, `version_id` и `file_id`; выбранные и созданные сущности сохраняются в `st.session_state`.

| Шаг | Действие пользователя | Результат |
|---|---|---|
| 1. Набор данных | Заполнение названия, описания и категории | Создается запись в `datasets` |
| 2. Версия | Ввод номера версии, статуса, уровня доступа и источника | Создается запись в `dataset_versions` |
| 3. Метаданные | Заполнение аннотации, методики, охвата, лицензии и качества | Создается или обновляется `dataset_metadata` |
| 4. Файл | Загрузка CSV/XLSX-файла | Файл сохраняется в `storage/`, сведения фиксируются в `dataset_files`, выполняется проверка |
| 5. Импорт наблюдений | Запуск импорта | Корректные строки сохраняются в `observations` |
| 6. Проверка результата | Переход к карточке набора | Пользователь видит созданный набор, версию, файл, метаданные и наблюдения |

Отдельные страницы старого сценария сохранены. Пользователь по-прежнему может вручную перейти на `Создание версии`, `Метаданные версии`, `Загрузка файла` и `Карточка набора данных`.

### Загрузка, проверка и импорт

При загрузке файл связывается с конкретной версией набора данных. Файл сохраняется в `storage/`, а в базе создается запись в `dataset_files`.

Валидация проверяет:

- поддерживаемый формат CSV/XLSX;
- возможность чтения файла;
- непустой файл;
- наличие обязательных колонок `region`, `agro_object`, `indicator`, `unit`, `period_year`, `value`;
- числовой формат `period_year`;
- числовой формат `value`.

При импорте дополнительно проверяется наличие значений в справочниках регионов, агрообъектов, показателей и единиц измерения. Корректные строки сохраняются в `observations`, ошибки справочников фиксируются и показываются пользователю.

### Обработка дублей файлов

В MVP реализована базовая обработка повторной загрузки файлов:

- для файла вычисляется SHA-256 checksum;
- при загрузке проверяется наличие файла с тем же checksum в пределах версии;
- при совпадении пользователю выводится предупреждение;
- одинаковые имена в интерфейсе отображаются различимо, например `file.csv`, `file (2).csv`;
- повторно загруженный файл сохраняется отдельной записью в `dataset_files`;
- при повторном импорте дубля наблюдения от предыдущих дублей заменяются, чтобы не размножать одинаковые строки в `observations`.

Это не является полноценной промышленной дедупликацией, но закрывает главную проблему MVP: повторный импорт одного и того же файла не должен бесконечно увеличивать количество одинаковых наблюдений.

### Карточка набора и переключение версии

Карточка набора данных объединяет общие сведения, текущую версию, список всех версий, метаданные, файлы, скачивание, экспорт и первые строки наблюдений.

В MVP реализовано переключение текущей версии набора. Пользователь может выбрать одну из существующих версий и назначить ее текущей. Это важно для демонстрации версионности и возможности перехода к предыдущему состоянию данных.

### Скачивание и экспорт

В карточке набора доступны:

- скачивание исходного файла;
- экспорт структурированных наблюдений текущей версии в CSV.

Обе операции фиксируются в `data_exports`. Журнал экспортов доступен на отдельной странице `Журнал экспортов`.

### Административное удаление

Для пользователя с ролью `admin` реализованы:

- удаление набора данных;
- удаление версии;
- удаление файла.

Ограничение MVP: удаление физическое. Soft delete, восстановление удаленных данных, журнал причин удаления и полноценный `audit_log` не реализованы.

## 3.4 Тестирование, оценка результатов и ограничения

### Фактический результат тестов

Команда:

```bash
docker compose exec -T backend pytest
```

Фактический результат:

```text
10 passed, 3 warnings
```

Предупреждения не связаны с падением тестов: они относятся к deprecated `crypt` в `passlib` и deprecated `on_event` в FastAPI.

### Покрытие тестов

| Файл теста | Проверяемые сценарии |
|---|---|
| `test_health.py` | Проверка `GET /health` |
| `test_datasets.py` | Создание набора, версии и метаданных; переключение текущей версии; удаление файла, версии и набора; запрет удаления обычному пользователю |
| `test_validation.py` | Успешная проверка CSV; ошибка при отсутствии обязательной колонки; повторная загрузка файла-дубля и импорт без размножения наблюдений |
| `test_exports.py` | Импорт observations, экспорт CSV и запись операции в `data_exports` |

Frontend/e2e-тесты на текущем этапе не реализованы.

### Ограничения MVP

| Направление | Ограничение |
|---|---|
| Авторизация | Demo-вход, нет JWT/OAuth |
| Ролевая модель | Таблицы ролей есть, но нет промышленной RBAC-модели |
| Миграции | Нет Alembic, используется `create_all` |
| Удаление | Физическое удаление, нет soft delete |
| Аудит | Есть `data_exports`, но нет общего `audit_log` |
| Источники версии | Нет `version_sources`, источник хранится в `dataset_versions.source_id` |
| Статусы | Нет `version_status_history` |
| Проверка | Нет `validation_rules`, правила заданы в коде |
| Геоданные | Нет PostGIS, регионы являются справочником |
| Интеграции | Нет внешних ФГИС/API-интеграций |
| Ключевые слова | Таблицы есть, UI/API управления нет |
| Демо-данные | Seed не создает готовые demo-наборы |
| Тестирование | Нет frontend/e2e-тестов |
| Деплой | Production-деплой не реализован, используется локальный Docker Compose |

## Итоговая формулировка для главы 3

Фактическая реализация MVP-прототипа подтверждает работоспособность базового жизненного цикла репозитория сельскохозяйственных данных. В системе реализованы постоянная карточка набора, версия, метаданные версии, загрузка CSV/XLSX-файлов, базовая проверка структуры, импорт корректных строк в `observations`, просмотр карточки, скачивание исходного файла, экспорт структурированных наблюдений и фиксация операций в `data_exports`.

Наиболее важным результатом является сохранение принципа разделения `datasets` и `dataset_versions`. Это позволяет относить изменяемые сведения к конкретной версии и не смешивать их с постоянной карточкой набора данных.

Дополнительно в текущей версии MVP реализованы пошаговый мастер создания набора, переключение текущей версии, предупреждение о повторной загрузке файлов-дублей, предотвращение размножения наблюдений при повторном импорте дублей и административное удаление набора, версии или файла.

При этом прототип следует оценивать именно как MVP. Он не является промышленной платформой и не реализует все компоненты полной модели v4.1. Ограничения текущей версии должны быть явно отражены в тексте ВКР и отнесены к направлениям дальнейшего развития.
